# Design

Why the stack is built the way it is. For installation and day-to-day
operation, see [deployment.md](deployment.md).

---

## 1. Goal

One `docker-compose.yml`, deployable from Portainer, that brings up a complete
and self-contained Jitsi Meet server. No reverse proxy on the host, no manual
steps, and no domain, credential or plugin written into the code.

Everything a deployment needs to state:

| Setting | Where |
|---|---|
| Jitsi version (Docker tag) | `.env` |
| Public domains served | `.env` |
| Prosody plugins to install | `.env` |
| Plugin configuration | `conf/prosody/plugin-conf/` |
| Sub-path routes, per domain | `conf/routes.conf` |
| Whether Let's Encrypt issues certificates | `.env` |
| Certificate and key, when supplied | `conf/certs/` |
| Additional CA to trust | `.env` |

## 2. Architecture

### 2.1 Services

Images are pinned to a rolling stable tag rather than a version number. The
stack uses no recent or unusual nginx feature, so tracking `stable-alpine`
costs nothing and avoids a pin that quietly rots. Only `JITSI_VERSION` is an
exact tag, because there the whole point is to choose the release.

| Service | Image | Published ports | Role |
|---|---|---|---|
| `init` | `alpine` | -- | Renders generated files, then exits |
| `nginx` | `nginx:alpine` | 80/tcp, 443/tcp | Reverse proxy and TLS demultiplexer |
| `coturn` | `coturn/coturn` | 443/udp | STUN and TURN |
| `web` | `jitsi/web` | -- | Frontend |
| `prosody` | `jitsi/prosody` | -- | XMPP server |
| `jicofo` | `jitsi/jicofo` | -- | Focus component |
| `jvb` | `jitsi/jvb` | 10000/udp | Video bridge |
| `acme` | `neilpang/acme.sh` | -- | Certificate issuance and renewal |

### 2.2 Sharing port 443

HTTPS and TURN over TLS both want the one port a restrictive firewall is likely
to allow. nginx runs its `stream` and `http` blocks at once and tells the two
protocols apart by the ALPN of each connection:

```
                        ALPN "stun.turn" ──→ 127.0.0.1:8444 ──→ coturn:5349
:443/tcp ──→ stream ────┤
             ssl_preread  anything else  ──→ 127.0.0.1:8443 (HTTPS)

:443/udp ──────────────────────────────────→ coturn:443
:10000/udp ────────────────────────────────→ jvb
```

This is the arrangement the official `jitsi-meet-turnserver` package uses.

**The relay port range is not published.** In TURN the client only ever talks
to the server on its listening port. The `min-port`/`max-port` range faces the
*peer* -- here the video bridge, on the stack's own network -- so that traffic
never leaves the host and needs no firewall rule.

### 2.3 Preserving the client address

A `stream` proxy forwards raw TCP, so the HTTPS server behind it would see
`127.0.0.1` as the source of every request. That would silently defeat any IP
allow-list. The splitter therefore sends the PROXY protocol header, and
`site-defaults.conf` restores the real address:

```nginx
# stream
proxy_protocol on;

# http
listen 8443 ssl proxy_protocol;
set_real_ip_from 127.0.0.1;
real_ip_header   proxy_protocol;
```

coturn cannot read that header, so a second `stream` server consumes it and
forwards plain TCP. **Known limitation:** coturn logs the proxy's address
rather than the client's for TURN-over-TLS connections. Its peer rules are
unaffected, and the official Jitsi deployment behaves the same way.

### 2.4 Resolving upstreams at request time

Every upstream is named through a variable with a `resolver` configured:

```nginx
set $web_backend "http://web:80";
proxy_pass $web_backend;
```

Without this, nginx resolves each name once at startup and caches it forever. A
container recreated with a different address would then receive no traffic
until nginx restarted. It also lets nginx start while coturn is still down.

### 2.5 Keeping coturn from being abused

A TURN server on a well-known port is a standing invitation to relay abuse.
`conf/coturn/turnserver.conf.template` closes it down:

- `use-auth-secret` with a secret shared with Prosody, which turns it into
  time-limited credentials. A client never receives a static password.
- `no-multicast-peers`, `no-tcp-relay`, `no-cli`.
- Every private and reserved range denied, with the stack's own subnet allowed
  back so relayed media reaches the bridge.

The subnet is pinned in the compose file rather than left to Docker, because
the allow-list has to name it exactly.

**One decision changed during design.** The shared secret was going to be
generated by `init` on each stack recreation. It cannot be: Prosody reads it
from its environment, and a value produced after the containers start never
reaches it. It is therefore a literal in `.env`, and `scripts/gen-secrets.sh`
rotates it.

## 3. Independence from the Jitsi release

The stack must work with **any `stable` tag**. `JITSI_VERSION` is the only
place a version appears. Nothing in the design may depend on the internals of
one release:

| Risk | How it is avoided |
|---|---|
| Configuration templates change between releases | No generated configuration is frozen. Only additive files. |
| Environment variables appear, get renamed or disappear | The compose file enumerates no variable names: it uses `env_file`. |
| Images change init system (s6-overlay v2 to v3) | The extra CA is a configuration setting, not a startup script. |
| Dynamic branding JSON keys change | The JSON is an editable file, not generated. |
| Internal image paths move | Bind mounts over internal paths are optional and documented as fragile. |

The second row matters most. A stock `docker-compose.yml` lists around 150
variables by name in each service. That list is why configuration drifts on
upgrade: a variable added upstream needs a compose change, and one removed sits
there dead. With `env_file` the whole environment is passed through and any
variable the image supports works untouched.

### 3.1 Relationship to the upstream compose file

This stack **does not extend, include or vendor** the Jitsi project's
`docker-compose.yml`. It declares the four Jitsi services itself and pulls the
official images.

That is deliberate. Compose's `extends:` and `include:` need a local copy of
the file being extended, so using them would mean vendoring upstream's compose
and re-syncing it on every release -- reintroducing exactly the drift this
design avoids. Upstream's file is also a template meant to be edited, not a
base meant to be composed onto.

**The contract with upstream is the images and their environment variables,
not the compose file.** All the configuration logic -- the templates that turn
`XMPP_MUC_MODULES` or `ENABLE_LOBBY` into Prosody and JVB configuration -- lives
inside the images. Taking the images and passing them a complete environment
gets all of it. That is why `env_file` works, and why a new upstream release
usually needs nothing here but a different tag.

What is lost by not tracking upstream's compose: if a future release adds a new
*service* (as Jibri or Jigasi are today), it has to be added here by hand. That
is a rare, deliberate change, unlike a variable rename.

## 4. Configuration is generated, never frozen

A common way to customise Jitsi is to bind-mount a finished
`jitsi-meet.cfg.lua` read-only over the Prosody container. That defeats the
image's template: environment variables stop having any effect, and every
upgrade means rebuilding the file by hand against the new template.

This stack does the opposite:

| What | How |
|---|---|
| `jitsi-meet.cfg.lua` | Generated by the image from the environment. Never touched. |
| Plugin configuration | *Additional* `stack-*.cfg.lua` files written next to it. |
| Secrets | Rendered from `.env` into templates. Never literals in the repository. |

`init` writes those fragments into the same directory the Prosody container
mounts as `/config`, so they sit alongside the generated file instead of
replacing it.

Templates use `@PLACEHOLDER@` markers rather than `${VAR}`, so nginx's own
`$variables` and Lua syntax survive substitution untouched.

## 5. Prosody plugins

### 5.1 The four places a plugin has to be wired in

A Prosody plugin is not one setting. It only works when all four are true, and
the stack covers them in different ways:

| # | Requirement | Who satisfies it |
|---|---|---|
| 1 | The `.lua` file is on disk in a searched path | `init` downloads it into `conf/prosody/plugins/`, which the compose file mounts at `/prosody-plugins-custom` |
| 2 | That path is in `plugin_paths` | The Jitsi image's own template. `/prosody-plugins-custom` has been in it for years and is still there in `stable-11031` |
| 3 | The module is enabled on the right host or component | `XMPP_MUC_MODULES`, which the image renders into the MUC component's `modules_enabled` |
| 4 | The module's own options are set on that component | A fragment written by `init` into `conf.d/` |

Only #1 and #4 are ours. #2 and #3 are the image's, driven by a documented
environment variable, which is what makes the arrangement portable.

### 5.2 Why a separate fragment is safe

The fragments re-declare the component the generated file already declares:

```lua
Component "muc.meet.jitsi" "muc"
    muc_room_notification_url = "..."
```

Prosody's config loader handles a repeated `Component` by **merging key by
key**, not by replacing the block: `env.Component` calls `set()` per option on
the existing host table. Re-declaring is an error only when the name clashes
with a `VirtualHost`, which is not the case here.

**Order is undefined, and nothing may depend on it.** Prosody expands the
`Include "conf.d/*.cfg.lua"` glob with `lfs.dir`, which does not sort. The
fragments are therefore written so that each sets only keys no other file sets
— disjoint key sets merge to the same result in any order. The file names carry
no numeric prefix, so as not to imply an ordering that does not exist.

This is also why the generated `jitsi-meet.cfg.lua` is never replaced: doing so
would make the result depend on which file the filesystem happened to return
first.

### 5.3 Downloads

`init` reads `PROSODY_PLUGINS`, a list of URLs, and downloads each into
`conf/prosody/plugins/`. A download that fails leaves the copy already on disk
in place, so the stack starts with the last known-good plugin rather than
refusing to come up because a remote host is unreachable.

### 5.4 What can break on a Jitsi upgrade

Honestly assessed, weakest first:

| Risk | Likelihood | What happens | Mitigation |
|---|---|---|---|
| **The plugin uses a Prosody API that was removed** | **High** | The module fails to load; moderation silently stops working | Pin the plugin to a revision, not a branch, and re-check it when `JITSI_VERSION` changes |
| `ssl.cafile` stops being honoured by Prosody's HTTP client | Low | Notifications fail TLS verification | Bind-mount the bundle over the system trust store instead (§8) |
| `XMPP_MUC_MODULES` is renamed | Low | The module is never enabled | Rename the variable; `env_file` means no compose change |
| `plugin_paths` drops `/prosody-plugins-custom` | Very low | The module is not found | Add a fragment setting `plugin_paths` |
| Prosody starts sorting or erroring on repeated `Component` | Very low | Config error at startup, visible immediately | Merge the fragments into one file |

The first row is not hypothetical. `stable-11031` ships **Prosody 13.0.6**,
where `usermanager.is_admin` still exists but logs
`Usage of legacy is_admin() API, which will be disabled in a future build` on
every call, and already errors outright if `strict_deprecate_is_admin` is set.
A plugin written against that API works today and will stop working, without
any change on this side.

**This is the real compatibility boundary, and it is in the plugin, not in the
wiring.** Pin plugins to a commit and treat a Jitsi upgrade as a reason to
re-check them.

## 6. Domains and routes

Every domain in `JITSI_DOMAINS` is served by the same instance and shares one
room namespace. Room names are UUIDs, so they cannot collide.

Signalling always points at `PUBLIC_URL`, whichever domain served the page,
which is why the generated server blocks send permissive CORS headers.

`conf/routes.conf` declares which sub-paths go elsewhere:

```
<domain>  <path-regex>  <target>  [mirror=<url>,...] [host=<name>]
```

`target` may also be `redirect:<status>:<location>`. A `mirror` target receives
a copy of the request and its response is discarded, which is how one
deployment fans a notification out to several backends.

### Sites that are not Jitsi

A host reverse proxy usually serves more than Jitsi. Those vhosts vary too much
to generate -- separate certificates, extra listening ports, IP allow-lists,
their own snippets -- so they are dropped into `conf/nginx/sites/*.conf` and
included verbatim.

To keep files written for a host nginx working, the stack publishes the usual
snippets at the usual paths: `/etc/nginx/site-defaults.conf`,
`proxy-defaults.conf`, `only-trusted-hosts.conf` and `no-robots.conf`.
`site-defaults.conf` carries the `listen` directive, so a drop-in file never
has to know which internal port the splitter forwards to.

Two changes are needed in a migrated file:

1. `localhost` and `127.0.0.1` now mean the container. Use
   `host.docker.internal`, which the compose file maps to the Docker host.
2. Certificate paths move under `conf/certs/`.

**Reaching those backends.** When the backend is itself a container -- which it
usually is -- the stack creates a shared network (`EDGE_NETWORK`) that other
stacks join as external. The backend then publishes no port at all and nginx
addresses it by service name. That is strictly better than publishing a port:
the service becomes unreachable from outside the host, and correctness no
longer depends on a firewall rule. Both approaches require a change in the
other stack, so the shared network costs nothing extra.

For a backend running on the host outside Docker there is no network to share,
and `host.docker.internal` is used instead. Such a service still has to listen
on an address a container can reach, which loopback is not.

### The container console

If the console used to redeploy the stack is proxied *by* the stack, a bad
nginx configuration takes it down and there is no way back in. Its vhost can
live in `conf/nginx/sites/`, but a direct route that does not pass through the
stack -- its own port on the host, firewalled to trusted addresses -- has to
stay.

---

### Restricting by source address

`only-trusted-hosts.conf` is generated from `TRUSTED_HOSTS`. No address is ever
built into the repository: a list of who may reach an administrative endpoint
is deployment data, not code.

Empty means nothing is trusted and the file contains `deny all`. That is
deliberate. An allow-list with nothing allowed that let everyone through would
silently remove the restriction the site file is asking for, and nothing would
look wrong. Failing closed is visible immediately.

An operator-supplied `conf/nginx/snippets/only-trusted-hosts.conf` takes
precedence, for rules a flat list cannot express.

## 7. Certificates

Three mutually exclusive modes, chosen with `TLS_MODE`:

| Mode | Behaviour | Wildcards |
|---|---|---|
| `files` (default) | Uses `TLS_CERT_FILE` and `TLS_KEY_FILE` as they are. | as supplied |
| `acme-http` | acme.sh issues over HTTP-01, all domains as SAN. | no |
| `acme-dns-azure` | acme.sh issues over DNS-01 against Azure DNS. | yes |

acme.sh is used rather than certbot because its official image supports Azure
DNS natively, with no plugin and no image to build, and does HTTP-01 as well.
It is also the client the Jitsi web image uses internally. Azure credentials
are environment variables; no resource group or zone file is needed, because
acme.sh discovers the zone.

### Reloading after renewal

nginx and coturn both hold the certificate open. Rather than give the ACME
container access to the Docker socket, it touches a marker file after
installing a new certificate. nginx polls it and reloads; coturn polls it and
exits, letting the restart policy bring it back with the new certificate.
Certificates change a few times a year, so polling is cheap.

The watchers run **only under an ACME mode**. With `TLS_MODE=files` nothing
renews behind the containers' backs: the operator replaces the file and
restarts. A watcher there would be a background job that never fires, and one
that keeps the container alive after its entrypoint finishes -- which would
hang a one-shot configuration check.

## 8. Trusting an additional CA

`EXTRA_CA_FILE` names a CA certificate the containers must trust -- for
instance when room notifications go to an endpoint signed by a private CA.

`init` concatenates the system bundle with it into `conf/certs/ca-bundle.crt`
and writes a Prosody fragment pointing `ssl.cafile` at the result. It also
appends it to its own trust store, so plugin downloads from an internal host
work.

Doing it through configuration rather than a startup script keeps it working
regardless of which init system the Jitsi images use in a given release.

> If a future Prosody release ignores `ssl.cafile` for its outgoing HTTP
> client, the fallback is to bind-mount `ca-bundle.crt` over
> `/etc/ssl/certs/ca-certificates.crt` in the `prosody` service.

## 9. Branding

Overwriting files inside the image is avoided. In order of preference:

| Mechanism | Covers |
|---|---|
| `DYNAMIC_BRANDING_URL`, served from `conf/branding/` | Logo, premeeting background, colours, theme. Can differ per domain. |
| `custom-interface_config.js`, appended by the image | Application name, provider name, watermarks, links |
| `custom-config.js`, appended by the image | Options with no environment variable |
| `/config/nginx-custom/*.conf` | Serving your own assets |

**No official mechanism:** `favicon.ico`, `apple-touch-icon.png`, the PWA icons
and `manifest.json`. These still need a bind mount over an internal image path,
which is fragile across upgrades. Offered as an option, not the default.

## 10. Media

| Variable | Meaning |
|---|---|
| `DOCKER_HOST_ADDRESS` | Address of the host on its local network |
| `JVB_ADVERTISE_IPS` | Public address advertised to clients. Empty means discover over STUN |
| `JVB_STUN_SERVERS` | Empty once the stack's own coturn is reachable, so nothing external is needed |
| `JVB_WS_SERVER_ID` | Set to the service name, so the colibri WebSocket address survives container recreation |

XMPP and colibri WebSockets are on. `XMPP_DOMAIN` stays at `meet.jitsi`,
because issued JWTs declare it and moving it invalidates every one of them.
